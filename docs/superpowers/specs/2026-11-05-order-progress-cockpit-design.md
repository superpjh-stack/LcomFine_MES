# 수주별 공정 진행현황 운영보드 설계

## 1. 목적

홈 대시보드 맨 앞에 수주 이후 자재·생산·검사·출하까지의 진행 상태를 수주별로 보여주는 운영보드를 추가한다. 경영진은 전체 병목과 지연 수를 즉시 확인하고, 생산·출하 담당자는 특정 수주의 현재 단계와 다음 조치를 클릭 한 번으로 확인할 수 있어야 한다.

현재 시스템에 이미 있는 `production_request` 기반 추적 데이터와 `TRK-010`의 단계 계산을 재사용한다. 신규 업무 데이터를 저장하지 않으며, 홈 화면을 열 때 현재 상태를 조회한다.

## 2. 확정된 방향과 가정

- 사용자: 관리자·경영진과 생산·출하 담당자 모두.
- 표현: 상단 전체 요약 + 중앙 전체 공정 흐름 + 하단 수주별 진행 트랙.
- 애니메이션: 운영형. 실제 상태 변경·현재 진행 단계만 은은하게 강조하고 반복 재생하지 않는다.
- 기존 단계: `수주 → 지시 → 생산 → 검사 → 제품 입고 → 출하`.
- 자재 단계: 1차에서는 `자재 발주/입고`로 묶는다. 현행 스키마에서 발주 원천보다 원자재 입고·불출·LOT 연결이 명확하므로, 발주 데이터가 연결되기 전에는 자재 상태를 추정하지 않는다.
- 기준: 취소되지 않은 생산의뢰. 수주별 정렬은 지연 우선, 납기 임박, 최근 수주 순.
- 권한: 홈 접근 권한을 따르되, 상세 링크는 사용자의 기존 화면 권한을 확인한다.

## 3. 화면 설계

### 3.1 상단 요약

홈 화면 첫 섹션을 `수주 진행현황`으로 배치한다.

요약 카드는 다음 네 가지다.

| 카드 | 의미 | 링크 |
|---|---|---|
| 전체 진행 수주 | 취소 제외 수주 건수 | TRK-010 또는 RPT-010 |
| 정상 진행 | 현재 단계가 있고 납기 내 진행 중인 수주 | 해당 수주 목록 필터 |
| 주의 | 납기 7일 이내 또는 다음 단계 대기 | TRK-020 |
| 지연 | 납기 초과 미출하 또는 위험 상태 | TRK-020 지연 필터 |

데이터가 없거나 미연결된 경우 0으로 임의 표시하지 않고 기존 원칙대로 `미수집` 또는 `연계 전`으로 표시한다.

### 3.2 전체 공정 흐름

수주 집계값을 단계별로 보여준다.

`수주 → 자재 발주/입고 → 생산 → 검사 → 제품 입고 → 출하`

각 단계에는 건수와 상태를 표시한다.

- 정상: 녹색 상단선
- 대기/주의: 황색 상단선
- 지연/위험: 적색 상단선
- 집계 불가: 회색 + `미수집`

단계 카드는 기존 리포트 또는 추적 화면으로 이동하는 링크를 유지한다. 단계 사이의 화살표는 CSS로 표현하되, 화살표 자체를 계속 움직이지 않는다.

### 3.3 수주별 진행 트랙

각 수주는 한 줄의 가로 트랙으로 표현한다.

```text
SO-2026-001  고객A  제품X  ●━━●━━◉━━○━━○━━○  생산 중  D-5
```

행 구성:

- 수주번호, 거래처, 품목
- 6단계 진행 트랙
- 현재 단계명
- 납기와 D-day
- 진행률 또는 출하 잔량
- 상태 배지

단계 상태는 다음 네 가지다.

| 상태 | 의미 | 시각 표현 |
|---|---|---|
| 완료 | 해당 단계의 완료일·수량이 있음 | 채워진 원 + 체크 |
| 진행 | 마지막 완료 단계 다음 작업이 진행 중 | 강조 원 + 짧은 pulse |
| 대기 | 아직 시작되지 않음 | 빈 원 |
| 문제 | 지연·보류·불합격·데이터 불일치 | 경고 배지와 색상 |

행 클릭 시 기존 `TRK-010?request=...` 상세로 이동한다. 상세 권한이 없으면 행은 링크 없이 읽기 전용으로 렌더링한다.

### 3.4 선택 수주 상세

1차 구현에서는 별도 SPA drawer를 만들지 않고 기존 추적 상세 화면으로 연결한다. 이렇게 하면 데이터 계산을 중복하지 않고, 단계별 날짜·수량·담당부서·지시별 수량을 이미 제공하는 화면을 재사용할 수 있다.

향후 사용성 검증에서 행 클릭 후 페이지 이동이 느리다고 확인되면, 같은 응답에 상세 데이터를 포함하는 drawer로 확장한다.

## 4. 데이터 계약

홈 라우터가 `home_progress(user)` 조회 함수를 호출하고, 템플릿에는 다음 구조를 전달한다.

```python
{
  "summary": {
    "total": 24,
    "normal": 16,
    "warning": 5,
    "late": 3,
    "asof": "2026-11-05"
  },
  "flow": [
    {
      "key": "request",
      "label": "수주",
      "count": 24,
      "status": "정상",
      "href": "/trk/orders"
    }
  ],
  "orders": [
    {
      "request_no": "SO-2026-001",
      "customer_name": "고객A",
      "item_code": "ITEM-01",
      "item_name": "제품X",
      "qty": 100,
      "shipped_qty": 0,
      "remaining_qty": 100,
      "due_date": "2026-11-10",
      "d_day": 5,
      "current": "생산",
      "status": "정상",
      "stages": [
        {"key": "request", "label": "수주", "state": "done", "on": "2026-11-01", "qty": 100},
        {"key": "material", "label": "자재", "state": "done", "on": "2026-11-02", "qty": 100},
        {"key": "production", "label": "생산", "state": "active", "on": None, "qty": 60},
        {"key": "inspection", "label": "검사", "state": "pending", "on": None, "qty": None},
        {"key": "receipt", "label": "제품 입고", "state": "pending", "on": None, "qty": None},
        {"key": "shipment", "label": "출하", "state": "pending", "on": None, "qty": None}
      ],
      "href": "/trk/orders?request=SO-2026-001"
    }
  ],
  "truncated": False
}
```

`orders`는 초기에는 최대 30건으로 제한하고, 나머지는 `전체 진행현황 보기` 링크로 보낸다. 대시보드 성능과 첫 화면 가독성을 위해 모든 수주를 한 번에 렌더링하지 않는다.

자재 상태는 다음 우선순위로 계산한다.

1. 연결된 작업지시에 원자재 불출이 있으면 `done`.
2. 원자재 입고·검사대기·불출대기 정보가 있으면 `active` 또는 `pending`.
3. 관련 자재 데이터가 없으면 `pending`이며 `자재 데이터 미연결`을 보조 문구로 표시한다.

검사 단계는 제품검사 판정과 기존 추적 단계 계산을 사용한다. 출하는 확정 출하만 완료로 인정한다.

## 5. 애니메이션·접근성

- 활성 단계 원: `pulse` 1.6초, 무한 반복은 최대 2회 후 정지.
- 새로 완료된 단계: 행 진입 시 400ms의 색상 전환.
- 연결선: 상태가 완료된 구간만 색상이 채워지며, 이동하는 점 애니메이션은 사용하지 않는다.
- `prefers-reduced-motion: reduce`에서는 모든 pulse·전환을 제거한다.
- 색상만으로 상태를 구분하지 않고 텍스트 배지와 `aria-label`을 함께 제공한다.
- 트랙은 키보드로 포커스 가능하며, 현재 단계는 `aria-current="step"`을 사용한다.
- 숫자와 상태는 애니메이션이 끝나기 전에 화면에 이미 존재해야 한다.

## 6. 실패·경계 처리

- 수주가 없으면 빈 상태 문구와 수주 등록/추적 화면 링크를 보여준다.
- 단계 데이터가 없으면 `미수집`을 표시하고 완료로 간주하지 않는다.
- 부분 데이터는 마지막으로 확인된 단계까지만 완료 처리한다.
- 취소 수주는 보드에서 제외한다.
- 출하 수량이 수주 수량보다 크면 `데이터 확인 필요` 상태를 표시한다.
- DB 조회 오류는 기존 홈 페이지 오류 처리 흐름을 따르며, 애니메이션을 위해 클라이언트에서 임의 데이터를 만들지 않는다.

## 7. 구현 범위

변경 예정 파일:

- `src/lcomfine/app/routers/home.py`: 홈용 진행 데이터 조회 및 컨텍스트 연결
- `src/lcomfine/app/templates/home/index.html`: 진행보드 최상단 마크업
- `src/lcomfine/app/static/style.css`: 진행 트랙·상태·반응형·애니메이션 스타일
- `src/lcomfine/app/static/app.js`: 필요 시 상태 변경 표시를 위한 최소 초기화만 추가
- `tests/`: 진행 단계 계산, 상태 분류, 취소 수주 제외, 수량 경계 테스트

기존 `TRK-010`, `RPT-070`, `RPT-080`의 의미와 계산은 변경하지 않는다. 신규 API나 신규 업무 테이블은 1차 범위에서 만들지 않는다.

## 8. 검증 기준

1. 홈 첫 섹션에서 요약·전체 흐름·수주별 트랙이 순서대로 보인다.
2. 진행·완료·대기·문제 상태가 데이터에 맞게 표시된다.
3. 각 수주 클릭이 기존 추적 상세로 연결된다.
4. 취소 수주가 집계되지 않는다.
5. 자재 미연결 데이터를 완료로 표시하지 않는다.
6. 수주 30건 초과 시 화면이 과도하게 길어지지 않고 전체 보기로 연결된다.
7. 모바일/좁은 화면에서는 트랙이 가로 스크롤되며 정보가 겹치지 않는다.
8. reduced-motion 환경에서 움직임이 제거된다.
9. 기존 홈 카드·납기 목록·오늘 처리한 건이 깨지지 않는다.
10. 관련 단위 테스트와 템플릿 렌더링 검증이 통과한다.
