## 1. 결함

### DEF-QA2-001 · 중대 · 후가공·슬리팅 롤 번호로는 생산 실적이 조회되지 않는다 — 담당 개발2

- **기대값**: goal.md G-08 「롤 번호 하나로 그 롤의 작업지시 · 조색 기록 · **생산 실적** · 검사 결과 · 출하가 조회된다」. `contracts/db-schema.md` §6 「생산 실적 — 인쇄 롤: `roll.work_result_id` → `work_result`. **후가공·슬리팅 롤: 계보를 거슬러 올라간 인쇄 롤의 실적**」.
- **실측**: 롤 이력(F-RLL-06 `GET /rll/history?no=<롤>`)의 「생산 실적」 칸이 인쇄 롤에서는 `실적 <id> · 시작~종료 · 실적 수량` 으로 나오지만, 후가공 롤과 슬리팅 롤에서는 `- (작업 실적은 인쇄 롤에만 있다)` 다. 설계도 예시의 슬리팅 롤 ①(출하된 롤): 독립 SQL 로는 조상 인쇄 롤의 실적 2건이 나오고 화면에는 0/2. 후가공 롤도 0/2.
- **왜 중대인가**: 출하되는 롤은 늘 후가공·슬리팅 롤이다. 클레임이 들어온 롤 번호에서 「어느 설비에서 언제 인쇄했고 정지·폐기가 있었는가」 로 가려면 역방향 추적 → 인쇄 롤 번호를 하나씩 → 롤 이력을 다시 여는 손작업이 필요하다. LOT 추적 화면도 실적을 보여 주지 않는다(§6-3). 키는 이어져 있다(SQL 로는 조회됨) — 화면이 그 길을 따라가지 않는다.
- **재현**
  ```bash
  uv run python tools/check_data.py --only G-08      # 「[화면] 후가공·슬리팅 롤 번호 → 그 롤의 생산 실적」 FAIL
  uv run pytest -q "tests/test_qa2_lineage.py::test_g08_roll_history_shows_production_result_for_finishing_and_slit_rolls"
  ```
  손으로: 설계도 예시를 만든 뒤 슬리팅 롤 번호로 `GET /rll/history?no=<슬리팅 롤>` → 「생산 실적」 칸.
- **고칠 곳(제안)**: `routers/rll.py` 의 `history` 와 `templates/rll/history.html` — `roll.work_result_id` 가 없는 롤은 계보를 거슬러 올라가 닿은 인쇄 롤들의 실적을 보여 준다(`lineage.trace_backward` 로 닿은 인쇄 롤 → `work_result`).

### DEF-QA2-002 · 중대 · splice 의 Job 지정으로 취소된 Job 에 롤이 생긴다 — 담당 개발2

- **기대값**: `function-list.md` F-JOB-03 「작업 실적·롤이 없는 Job 만 상태 `취소`」(= 취소된 Job 에는 롤이 없다) · F-POP-01 「취소·완료 Job 은 422」 · F-SHP-01 은 취소된 Job 의 출하 등록을 422 로 막는다. Job-Lot-Roll 의 Job 키가 살아 있는 Job 을 가리켜야 한다(G-08).
- **실측**: 같은 Job 의 인쇄 롤 2개를 `POST /rll/finishing/splice` 에 `job_no=<취소된 Job>` 과 함께 보내면 **HTTP 200**, 후가공 롤이 취소된 Job 아래에 만들어진다(취소 Job 의 롤 1개). 부모 롤 2개는 소진된다. 그 롤은 출하 등록이 막힌 Job 에 속하므로 정상 흐름으로는 출하할 수 없고, 롤을 지우는 기능도 없다. `완료` 로 마감한 Job 을 줘도 200 이다(실측) — 작업 시작은 `완료` Job 을 422 로 막는데 splice 로는 롤이 붙는다. 이쪽은 출하 등록이 되므로 롤이 갇히지는 않는다.
- **함께 본 것(결함이 아니라 사람 확인 §6-5)**: 부모와 아무 관계가 없는 `등록` Job 을 줘도 200 이다. D-203 은 「부모들이 서로 다른 Job 이면 Job 을 받아야 한다」 만 말하고, 줄 수 있는 Job 의 범위를 말하지 않는다.
- **재현**
  ```bash
  uv run python tools/check_data.py --only G-08      # 「[API] 롤의 Job 키를 지킨다 …」 FAIL — HTTP 200 · 취소 Job 의 롤 1개
  uv run pytest -q "tests/test_qa2_lineage.py::test_g08_splice_cannot_put_a_roll_under_a_cancelled_job"
  ```
  손으로: Job A 에서 인쇄 롤 2개 → Job X 등록 후 곧바로 취소(`POST /job/orders/{X}/cancel`) → 후가공 화면에서 롤 2개 스캔 → Job 번호 칸에 X → splice 등록.
- **고칠 곳(제안)**: `routers/rll.py` 의 `_finish`(또는 `lineage.make_finishing_roll`) — `job_no` 로 받은 Job 의 상태가 `등록` 이 아니면 422. 줄 수 있는 Job 을 「부모 롤들의 Job 중 하나」 로 좁힐지는 §6-5 의 답에 따른다.

## 5. 재지 못한 것

1. **G-11 — 테이블이 실제로 비었을 때의 6 화면**(롤 라벨 · 후가공 · 슬리팅 · 롤 이력의 최근 목록 · 출하 승인 · 현황판). 조건을 줄 수 없고 DB 를 비울 수 없어, 라우트는 그대로 돌리고 템플릿에 넘어가는 목록만 비워(`templating.render` 의 인자 · 현황판은 `stats.board` 의 날짜를 1990-01-01 로) 빈 상태를 그렸다. 「빈 줄이 `미수집` 인가」 는 쟀지만 「테이블이 정말 0행일 때 그 라우트가 죽지 않는가」 는 재지 못했다. 새 DB 에서 한 번 열어 보면 끝난다(`make db-reset` 직후 `make check-routes`).
2. **G-09 — 시드 밖 테이블까지 포함한 전체 행 수 diff.** 다른 QA 가 같은 DB 에 쓰는 중이라 시드가 넣은 행(등록자 `seed` + 역할·권한·채번 형식) 92개의 행 수와 내용만 대조했다. `sys_number_seq` 가 시드 재실행으로 안 올라가는지도 같은 이유로 재지 못했다(코드상 `seed_dev2` 는 넣을 때만 발번한다).
3. **G-05 — 시스템 관리 쓰기 4기능(F-SYS-01·02·03·06)의 동적 호출.** 사용자·권한 표를 바꾸면 다른 QA 의 측정이 흔들려서 부르지 않았다. 정적 스캔으로는 `sys_user` · `sys_permission` · `sys_access_log` 만 쓴다. 이관 배치의 적재 명령도 정적 스캔만 했다(동적은 QA3 의 G-15).
4. **G-06 — 진짜 브라우저 조작.** 폼 제출은 HTML 을 읽어 그대로 보낸 것이고 JS(스캔칸 포커스 · 확인 창 · 알림)는 돌지 않는다. 브라우저 한 바퀴는 QA3 의 G-22.
5. **집계의 시간대.** 「날짜가 기간 안」 은 DB 세션 시간대(`Asia/Seoul`)의 날짜로 재서 일치했다. 앱 서버의 `date.today()`(납기의 「오늘」 · 기본 기간)와 DB 의 `current_date` 가 다른 시간대인 배포는 재지 못했다(D-03 운영 환경 미정).

5. **splice 의 Job 지정 범위(D-203 · D-16).** 부모와 무관한 `등록` Job 을 줘도 받는다. 그러면 Job A 에서 만든 롤이 Job B 의 출하 LOT 에 실릴 수 있다(D-16 「출하 LOT 1 = Job 1」 을 돌아가는 길). 재작업·전용이 실제 업무라면 맞고, 아니라면 부모들의 Job 중 하나로 좁혀야 한다.
6. **출하가 걸린 Job 의 취소(F-JOB-03).** 계약은 「작업 실적·롤이 없는 Job 만 취소」 라 `등록` 상태의 출하(롤 0개)가 있는 Job 도 취소된다(실측 200). 반대쪽 F-SHP-01 은 취소된 Job 의 출하 등록을 막는다. 계약에 출하를 더할지 — 아키텍트·개발1.
7. **입고량을 넘는 투입(D-202).** 입고 100 인 LOT 에 9999 를 투입하면 200 이고 잔량이 −9899 가 된다. 이미 D-202 가 「현업 확인 필요」 로 적어 둔 것 — 실측만 보탠다.
8. **「Lot」 의 뜻과 추적의 출발 번호(D-10).** 설계도는 P9 의 입력을 「LOT 번호 또는 롤 번호」 라고 했다. LOT 추적은 원재료 LOT · 롤 · 출하 LOT 번호만 받고, 생산 LOT 번호(`job_lot.lot_no`)와 Job 번호는 검색 0건 · 추적 422 다. D-10 이 Lot 을 생산 LOT 으로 읽었으므로, 생산 LOT 번호로 추적을 시작할 수 있어야 하는지 묻는다.
9. **출하일에 제한이 없다.** `ship_date=1900-01-01` 도 등록된다(200). 납기 집계가 그 날짜로 준수/지연을 가르므로 오타 하나가 준수율을 바꾼다. 허용 범위를 둘지.
10. **미검사 롤의 출하(D-17) · 「5단 이상」 의 뜻.** 미검사 롤은 스캔·승인되고 COA 에 `미수집` 으로 나온다(실측 — D-17 이 이미 현업 확인으로 둔 것). G-07 의 「분기 5단 이상」 은 화살표 5개 이상의 길로 읽었다(만든 계보는 8~12).

## 9. 검사기 자체의 검증

「PASS 가 아무것도 안 읽고 나온 것이 아닌가」 를 두 가지로 막았다.

1. **읽은 양을 판정에 넣었다.** G-05 정적 스캔은 라우트로 이어진 기능이 94/94 가 아니면 FAIL 이다(처음에 이 FastAPI 가 `include_router` 한 라우터를 `app.routes` 에 풀지 않아 0개를 읽고 「위반 0」 으로 통과하는 것을 발견해 고쳤다). 동적 검사는 쓰기 기능 50/50 을 실제로 불렀어야 PASS 다.
2. **앱을 일부러 망가뜨려 본다** (`tests/test_qa2_sensitivity.py` 6건 — monkeypatch 로 이 프로세스 안에서만, `src/` 는 고치지 않는다).

| 일부러 넣은 고장 | 잡는 검사 | 결과 |
|---|---|---|
| 추적 재귀를 두 단에서 끊는다 (`lineage._WALK`) | 화면 추적 ≠ 독립 SQL | 잡음 |
| 부모 롤의 재고 검사를 없앤다 (`lineage.assert_usable`) | 막기 — 소진 롤 재사용이 「안 막힘」 | 잡음 |
