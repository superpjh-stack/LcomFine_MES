데이터가 누구에게서 들어와 어디에 쌓이고 어떻게 이어지는지를 사용자 → 업무 진행 → 데이터 흐름 → 계보 순서로 다시 그렸다. 정본은 설계도(그림 5 · 표 3, 2026년 10월 · 2안 전체개발 기준)이고, 거기 없는 것은 코드 계약과 결정 대장에서 가져왔다.

1 · 사용자와 채널

1.5 로그인 · 세션 · 기록

  • 세션은 요청마다 DB 로 확인한다(D-26). 쿠키에는 누구의 어느 세션인지만 있고, 역할·상태는 sys_user 의 지금 값을 쓴다. 중지·잠금·로그아웃된 세션은 다음 요청부터 401, 역할 변경은 다음 요청부터 반영.
  • 접근 로그(G-18): 로그인 성공·실패, 화면 조회, 데이터 변경(누가 · 언제 · 무엇을)이 sys_access_log 에 남고 시스템 관리 > 로그에서 조회한다. 403 거부는 기록하지 않는다(D-410 · 확인 필요).
  • 비밀(G-19): 비밀번호·세션 비밀은 저장소와 문서에 없다. 시드 비밀번호는 환경변수로만 준다.
  • 퀵 로그인(D-416 · 가설): 개발·테스트 환경에서만 켜지는 플래그. 로그인 화면 오른쪽에 역할별 계정을 보여 주고 한 번에 들어간다. 운영(prod)에서는 플래그를 켜도 꺼진다.

2 · 업무 진행 — 작업지시에서 출하 · 추적까지

프로세스끼리 직접 주고받지 않는다. 앞 화면이 만든 번호(Job · 원재료 LOT · 롤 · 출하 LOT)를 다음 화면이 스캔하거나 고른다. 라벨의 바코드를 스캔칸에 넣으면 그 번호의 화면이 열린다(G-14).

2.2 단계별 진행

  1. 기준정보를 세운다

    관리자생산 (인쇄 기준만)
    프로세스 P1쓰는 곳 D1채널 관리자 Web화면 /bas/* 5 · /prt/* 3
    • 품목(제품 / 원재료) · 고객 · 공정(인쇄 / 후가공 / 슬리팅 / 기타) · 설비 · 불량코드 · 판사양 · 아니록스 · 잉크조성(성분 · 비율).
    • 코드는 못 바꾸고, 삭제는 참조(Job · 원재료 LOT · 판사양 …)가 없을 때만 — 막는 참조는 DB FK 에서 읽는다(D-102).
    • 설비는 여기까지다. 상태·수집값 컬럼은 두지 않는다(G-12).

  2. 작업지시(Job)를 내린다

    관리자생산
    P2D2 참조 D1관리자 Web/job/orders · /job/mapping출력물 작업지시서
    • 품목 · 고객 · 수량 · 납기 · 판사양 · 아니록스 · 잉크조성 · 설비를 받아 Job 번호를 채번한다. 작업지시서에 바코드가 찍힌다.
    • Job-Lot-Roll 매핑 = Job 1 : 생산 LOT N(job_lot, D-10). 롤은 미리 묶지 않는다 — 실적이 만든다.
    • 상태 등록 → 완료 / 취소. 진행 중인 실적이 있으면 마감하지 못한다(D-107).

  3. 원재료를 입고한다

    생산현장
    P3D3 참조 D1현장 POP · 관리자 Web/mat/receipts · /mat/lots출력물 원재료 LOT 라벨
    • 입고 1건 = 원재료 LOT 1개. 품목(원재료) · 공급처 · 공급처 LOT · 수량 → LOT 번호 채번 → 라벨 출력(인라인 SVG 바코드).
    • 잔량은 저장하지 않고 계산한다 — 입고 수량 − 투입 합(v_material_lot_stock).

  4. 입고검사로 LOT 을 가른다

    품질
    P3D3현장 POP · 관리자 Web/mat/inspections권한 범위 입고검사 (괄호 조건 1)
    • LOT 스캔 → 대기 → 합격 / 불합격. 생산·현장은 이 화면을 보기만 한다 — 단추가 막히고 POST 는 403.
    • 합격 LOT 만 투입할 수 있다. 대기·불합격 LOT 의 투입 스캔은 422.

  5. 조색을 기록한다

    품질현장
    P4D4 참조 D2현장 POP/clr/records
    • Job 스캔 → 색 이름 · 색상값(L·a·b, ΔE 가 Lab 차이이므로 Lab 으로 가정, D-18) · 기준 잉크조성.
    • 배합비는 성분 행의 비율 합이 100 이어야 저장된다. 조색 기록은 Job 키로 롤과 이어진다(roll.job_id = color_record.job_id).

  6. 작업을 시작한다 — 정지 · 재개 · 폐기

    생산현장
    P5D5 참조 D2현장 POP/pop/work · /pop/stops
    • Job 스캔 → 설비 고르기 → 작업 시작(work_result 상태 진행). Job 행을 잠그고 상태를 다시 본 뒤 넣는다(D-211).
    • 정지 등록 ⇄ 재개(진행 ⇄ 정지), 폐기 등록(수량 · 단위 · 불량코드). 전부 D5 에만 쓴다 — Job 상태는 바꾸지 않는다.

  7. 자재를 투입한다 (LOT 스캔)

    생산현장
    P5D5 참조 D3현장 POP/mat/inputs?work_id=…
    • 진행 중인 실적에서 원재료 LOT 라벨을 스캔한다 → material_input 한 행. 같은 LOT 이 다른 실적에 또 들어가도 된다(설계도 §3 의 LOT ①).
    • 이 스캔이 작업 종료 때 인쇄 롤의 계보 투입 행이 된다(D-13).

  8. 작업을 종료한다 = 인쇄 롤이 태어난다

  • 쓰기 경계: 프로세스는 자기 저장소에만 쓴다. P9 · P10 은 어떤 테이블에도 쓰지 않는다. 라우터별 쓰기 SQL 정적 스캔과 조회 전후 행 수 diff 0 으로 확인한다(G-05).

4.3 DB 가 마지막으로 막는 것

lineage 가 먼저 검사해 사람이 읽을 문장으로 422 를 낸다. 놓쳐도 DB 제약과 트리거가 막고, 제약 위반은 500 이 아니라 422 로 바뀐다.

  • 순환: 자기 자신(CHECK) · 긴 순환(트리거가 자식에서 내려가 부모에 닿는지 본다, advisory lock 으로 직렬화). 계보 행의 부모·자식·관계는 UPDATE 불가 — 지우고 다시 넣는다.
